## Five shape-of-bug rules to apply on future PRs

1. **State-mutating tools must propagate into the caller's working set.** Any tool that registers, connects, installs, or otherwise extends what is callable next iteration must update the per-turn `tools` list as part of its call site — not rely on later "I remembered the name from history" mechanisms. The audit caught this on `connect_mcp_server` / `install_mcp_server`; check `add_mcp_server`, `favorite_mcp_server`, watcher creation, anything that adds rows the brain might want to use immediately.
2. **Hardcoded enums silently shadow other sources of truth.** `free_providers.PROVIDER_DEFS` is a hardcoded list of 5 providers; nothing in the type system tells you that `MODEL_CATALOG` exists alongside it and that they describe overlapping concepts. When you find a hardcoded list, search for the truth-table equivalent elsewhere and either delete one or write the bridge.
3. **Whole-message regex anchors are brittle to known wrappers.** `^check my upwork inbox$` works for hand-typed input and fails for `[JOB:…] check my upwork inbox` (cron) and `hey can you check my upwork and tell me X` (user). Strip known wrappers first, then anchor on the cleaned core. Unknown wrappers must fall through — never strip-blind.
4. **When the runtime narrows a tool list to enforce dispatch, it MUST be able to synthesise the dispatch itself.** Two failure modes were both stacking on this: AUTO-PROMOTE narrowed to `run_background` only, brain refused; hallucination-cap then bailed with an error instead of doing the call itself. If the runtime already knows what to dispatch, it shouldn't depend on the brain agreeing.
5. **Managed crons must be lockable.** `EditJobSkill` is power-tool enough to break the runtime's invariants. Any cron that the rest of the system depends on (`survival_message_check` for the upwork inbox fast-path, future watcher seeds, etc.) needs the same kind of immutability the canonical instructions table gives `survival_*`.
